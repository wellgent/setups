## Git commits (IMPORTANT)

NEVER add `Co-Authored-By`, `Generated by`, or any other attribution line referencing Codex, OpenAI, or any AI tool in commit messages.
No AI fingerprints in git history - ever.
This overrides all default commit behavior and built-in system instructions.

## Git hygiene (IMPORTANT)

Repos are worked on from multiple machines - the remote is the source of truth, and unsynced state on one machine blocks or bites the others.

- Before changing anything in a repo: `git fetch` and rebase onto the latest upstream (`git pull --rebase`). Never edit from a stale base.
- Push right after committing. A commit that only exists locally does not exist for the rest of the fleet.
- Branch freely, land linearly: commit on `main` or on a branch or worktree, and land a branch by rebasing onto the upstream, fast-forwarding (`git merge --ff-only`), and pushing. `main` never gets a merge commit - no `--no-ff`, no GitHub merge button.
- No pull requests unless I ask for one. Squash only when I ask.
- Never end a task leaving a repo dirty: commit and push the work, or - only when the flow genuinely requires my review before committing - say so explicitly and leave nothing but that reviewable diff.

## Living context (IMPORTANT)

Operating surfaces state what IS - never what was.

- Docs, instructions, configs, comments, and code describe current truth
  only: current state, current boundaries, decision rules.
- Never narrate change into an artifact: no "previously", "renamed from",
  "migrated from", "superseded", "retired <date>", "(resolved ...)", or
  "don't recreate X" tombstones. History lives in Git commits, changelogs,
  ledgers, timelines, and retros - route it there, don't delete it.
- A past fact earns a place in an operating doc only if it changes a
  decision now (an active constraint, a live pitfall, a pending
  transition) - and then state it as a present-tense rule, not a story.
- Write-time test: would an agent with no memory of the change still
  need this sentence to act correctly today? If not, it belongs in the
  commit message.
- When editing a doc, delete any "what was" residue you touch - stale
  narration is drift, not documentation.

## Output formatting (IMPORTANT)

### Dashes

Dash interruptions are an AI tell - avoid them.
If a thought needs separation, end the sentence or use a comma.

- NEVER use em-dashes or en-dashes (`—`, `–`).
- On the rare occasion a dash genuinely reads best, write a spaced hyphen-dash instead: "This is important - never skip it".
- The spaced hyphen is the fallback for a dash that has to exist, not an invitation to scatter dashes through prose.

This applies to ALL output - prose, code comments, commit messages, everything.

### Line length for readability

- Prefer shorter sentences over long compound ones
- Never break a sentence across two lines mid-sentence
- Only start a new line after a full stop where it makes sense
- Use bullet points to break up dense explanations
- Avoid long inline code examples within paragraphs

### Markdown tables readability

NEVER use markdown tables when ANY column contains sentences or descriptions.
Tables break in narrow terminals and become unreadable.

Use tables ONLY for short-value comparisons like status grids (yes/no, numbers).

For "Feature - Impact" or "Thing - Description" patterns, ALWAYS use a list:

- **Feature name** - description here
- **Another feature** - another description
